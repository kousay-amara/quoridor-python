\section*{Introduction}

Quoridor is an abstract strategy board game designed by Mirko Marchesi and
first published in 1997 by the French company Gigamic. The game is played on a
square grid and is based on two simple actions: moving a pawn and placing
walls. Despite this apparent simplicity, the game exhibits a significant
strategic depth, as players must constantly balance progress toward their own
goal with the obstruction of their opponents.

The objective of this project is to design and implement a complete software
version of the game Quoridor, supporting two, three, or four players. The
program must strictly respect the official rules of the game and allow players
to interact through both a command-line interface and a graphical user
interface. In addition, the software must support configuration files,
internationalization, and robust error handling, in accordance with the
provided specifications.

This project goes beyond the development of a playable game. It aims to apply
fundamental software engineering principles, including modular architecture,
clear separation of concerns, automated testing, and comprehensive
documentation. Quoridor also represents an interesting case study from an
algorithmic perspective, as its gameplay can be naturally modeled using
graph-based representations and shortest-path algorithms, which are commonly
studied in computer science research.

\section{Historical Background and Existing Work}

Quoridor was invented by Mirko Marchesi in the mid-1990s and officially
released in 1997 by the French publisher Gigamic. Since its publication, the
game has gained international recognition for its elegant design and
educational value, receiving several prestigious awards such as the Mensa
Select Award in 1997 and the Games Magazine Game of the Year Award in 1998. Its
accessibility, combined with its strategic depth, has contributed to its
long-lasting popularity among both casual players and strategy game
enthusiasts.

Beyond its commercial success, Quoridor has attracted attention in academic
and technical contexts. The game's mechanics, which involve navigating a grid
while dynamically placing obstacles, make it a natural candidate for
algorithmic modeling. Several studies have explored Quoridor as a testbed for
artificial intelligence, pathfinding algorithms, and adversarial search
techniques.

In particular, previous academic work has shown that a Quoridor board can be
represented as a graph in which vertices correspond to board squares and edges
represent legal movements between adjacent squares. Wall placements
dynamically modify this graph by removing edges, while pawn jumps introduce
temporary alternative connections. Shortest-path algorithms such as
breadth-first search or Dijkstra's algorithm are commonly used to evaluate
positions, verify the legality of wall placements, and guide decision-making
in artificial intelligence agents.

Notable contributions include undergraduate and master-level research that
investigate heuristic evaluation functions, graph-based modeling, and search
strategies for Quoridor. These works highlight the computational complexity of
the game and demonstrate that, despite its simple rules, Quoridor poses
non-trivial challenges for both human players and automated systems. This
project builds upon these existing ideas while focusing primarily on the
design of a robust, extensible, and well-engineered software implementation.

\section{Game Classification and Complexity}

\subsection{Game Classification}

\textbf{Abstract combinatorial strategy game:}
\begin{itemize}
  \item No strong narrative theme and no randomness; the game relies entirely
    on logic and player decisions.
  \item In the case of Quoridor, the game is a pure logical confrontation
    between players.
\end{itemize}

\textbf{Perfect information game:}
\begin{itemize}
  \item There is no hidden information: the complete game state is known to
    all players at all times.
  \item In Quoridor, each player can see the positions of all pawns, all
    placed walls, and the number of walls remaining for each opponent.
\end{itemize}

\textbf{Deterministic game:}
\begin{itemize}
  \item Each action leads to a single, well-defined outcome, with no element
    of chance.
  \item As a consequence, adversarial search algorithms such as Minimax can be
    applied, since future game states can be fully predicted from the current
    state.
\end{itemize}

\subsection{State Space Complexity}

According to the thesis of Lisa Glendenning (2005), the state space of
Quoridor is estimated to be on the order of $10^{42}$ legal configurations
\cite{Glendenning2005}.
For comparison:
\begin{itemize}
  \item Checkers: approximately $10^{20}$ states.
  \item Chess: approximately $10^{46}$ states.
  \item Go: approximately $10^{172}$ states.
\end{itemize}

The state space complexity of Quoridor is therefore close to that of chess. As
a result, it is impossible to store all possible positions in memory or to
solve the game by brute-force methods, such as computing the optimal first
move exhaustively.

\subsection{Game Tree Complexity and Branching Factor}

At the beginning of a game, there are $8 \times 8 = 64$ possible positions for
placing a wall. Considering the two possible orientations (horizontal and
vertical), this yields 128 legal wall placements. In addition, a player
typically has up to 3 possible pawn moves. This results in a total of
approximately 131 legal moves at the start of the game.

According to Mertens (2006), the average branching factor of Quoridor is
around 60, which is relatively high \cite{Mertens2006}. For comparison: chess
has an average branching factor of about 35, and Go has a branching factor of
approximately 250. With a branching factor of 60, the size of the search tree
grows extremely fast. At depth 3, this leads to roughly
$60^3 \approx 216000$ nodes, compared to approximately 42000 nodes in chess.

Technical conclusion: it is essential to use alpha--beta pruning and to design
strong heuristic evaluation functions in order to make adversarial search
tractable.


\section{Rules of the Game}

This section describes the official rules of Quoridor as implemented in this
project. The objective is to provide a precise and unambiguous description of
the game mechanics so that a complete game can be played without
interpretation issues.

\subsection{Board and Components}

Quoridor is played on a square board composed of a 9×9 grid, resulting in 81
playable squares. The squares are connected orthogonally, allowing movement in
the four cardinal directions. Between these squares, grooves allow walls to be
placed in order to block movement.

Each player controls a single pawn. In addition, a fixed number of walls is
available and distributed among the players at the beginning of the game.
Walls are barriers that block movement between adjacent squares and play a
central role in shaping possible paths across the board.

\subsection{Initial Setup}

At the beginning of the game, the board is empty except for the players'
pawns, which are placed at predefined starting positions.

In a two-player game, one pawn is placed at the center square of the bottom
row, while the second pawn is placed at the center square of the top row. Each
player's objective is to reach any square on the opposite side of the board.

In a four-player game, pawns are placed at the center of each side of the
board: one on the top, one on the bottom, one on the left, and one on the
right. Each player must reach the side opposite their starting position.

In the two-player configuration, each player receives ten walls. In the
four-player configuration, each player receives five walls in order to
maintain balance and avoid excessive blocking.

Players alternate turns, starting with one of the players chosen according to
the game configuration.

\subsection{Pawn Movement}

On their turn, a player may move their pawn to an adjacent square. Movement is
allowed only in the four orthogonal directions: forward, backward, left, or
right. Diagonal movement is not allowed under normal circumstances.

A pawn may only move to an adjacent square if there is no wall blocking the
path between the two squares. Pawns cannot move outside the boundaries of the
board, nor can they move onto a square already occupied by another pawn.

The goal of pawn movement is to progress toward the target edge of the board
while navigating around walls placed by the opponents.

\subsection{Jump Rules}
If a pawn is located directly adjacent to an opponent's pawn and no wall
separates them, the player may jump over the opponent's pawn. The jump moves
the pawn to the square immediately beyond the opponent's pawn in the same
direction.

If a direct jump is not possible because a wall blocks the square behind the
opponent's pawn or because the board edge is reached, the player may instead
move diagonally to one of the two adjacent squares to the left or right of the
opponent's pawn, provided no wall blocks that diagonal movement.

In four-player games, a pawn may only jump over a single pawn per move.
Multiple consecutive jumps over different pawns are not allowed.

These jump rules ensure that pawns cannot be completely blocked by the
presence of other pawns and that movement remains possible even in crowded
situations.

\subsection{Wall Placement}

Instead of moving their pawn, a player may choose to place a wall, provided
they still have walls available. Walls are placed between squares and must be
oriented either horizontally or vertically. Each wall spans exactly two
adjacent square connections.

A wall placement must satisfy several constraints. Walls may not overlap or
cross existing walls, and they must fit entirely within the board's grooves.
Most importantly, a wall may not be placed if it completely blocks all
possible paths for any player to reach their target side.

To ensure this rule is respected, at least one valid path from each pawn's
current position to its goal edge must remain after the wall is placed. Pawn
positions do not block these paths, as pawns can always be jumped over under
the movement rules.

Once placed, walls are permanent and cannot be moved or removed for the
remainder of the game.

\subsection{Victory Condition}

The game ends immediately when a player moves their pawn onto any square of
their target edge. The first player to reach the opposite side of the board
wins the game.

In the standard rules of Quoridor, draws are rare and generally not expected
under normal play conditions, as players always have at least one legal move
available until a pawn reaches its goal.

\section{Algorithms and Data Structures}

This section describes the data structures and algorithms selected for the
implementation of the Quoridor game. The objective is to justify the chosen
representations and algorithmic approaches with respect to the rules of the
game and its inherent complexity, rather than to provide implementation-level
details.

\subsection{Board Representation}

The Quoridor board is a fixed-size square grid of dimension 9×9 in the
standard configuration. Each square represents a possible position for a pawn,
while walls block movement between adjacent squares. Internally, the board is
represented as a structured data object storing the positions of all pawns,
the placement and orientation of walls, and the board dimensions.

To support efficient rule validation and path analysis, the board
representation must allow fast queries about adjacency relations between
squares and the presence of blocking walls. This requirement naturally leads
to an abstraction that separates static board geometry from dynamic
connectivity.

\subsection{Graph-Based Modeling}

Following existing academic approaches, the board is modeled as a graph in
which each square corresponds to a vertex and each legal movement between
adjacent squares corresponds to an edge. Wall placements dynamically modify
this graph by removing edges, thereby blocking movement between affected
squares.

This modeling approach has been widely adopted in the literature, notably in
the work of Glendenning (2005), which formalizes Quoridor as a graph-based game
and uses graph traversal algorithms to analyze movement and wall legality
\cite{glendenning2005quoridor}. By representing the board as a graph,
pathfinding and connectivity constraints can be expressed in a uniform and
well-understood framework.

Pawn positions are treated separately from walls in this model. Since pawns
can be jumped over according to the rules, they do not permanently block
vertices or edges in the graph and are instead handled dynamically during move
validation.

\subsection{Pawn Movement and Jump Handling}

Basic pawn movement corresponds to traversing an edge between two adjacent
vertices in the graph. Jump mechanics introduce special movement cases when
two pawns are adjacent and no wall separates them. In such situations, a pawn
may jump over an opposing pawn to the square immediately beyond it, provided
that square is reachable.

If a direct jump is not possible due to a wall or the edge of the board,
diagonal movements are permitted under specific conditions. As suggested in
Glendenning's formalization, these jump rules are not encoded directly in the
static graph structure but are instead evaluated dynamically when determining
the set of legal moves available to a pawn at a given state. This approach
keeps the underlying graph representation simple while preserving full rule
correctness.

\subsection{Wall Placement Validation}

Wall placement is subject to strict legality constraints. In addition to
geometric restrictions such as non-overlapping and proper alignment, the rules
require that every player must retain at least one valid path from their pawn's
current position to their target edge after a wall is placed.

To enforce this constraint, the proposed wall placement is simulated by
temporarily removing the corresponding edges from the graph. A reachability
test is then performed for each pawn to verify that a path to the goal still
exists. This problem naturally reduces to a graph traversal task.

Both breadth-first search (BFS) and Dijkstra's algorithm are suitable for this
purpose. Since all movements have uniform cost, BFS is sufficient and more
efficient in practice. This approach is consistent with the methods described
in Glendenning (2005) and later works, which rely on shortest-path or
reachability checks to validate wall placements.

If at least one path exists for every player, the wall placement is accepted;
otherwise, it is rejected as illegal.

\subsection{Shortest Path Evaluation}

Shortest-path computations are also useful beyond wall validation. By
computing the minimum number of steps required for a pawn to reach its target
edge, the system can estimate player progress and relative advantage.

Such evaluations are commonly used in artificial intelligence research on
Quoridor, as described by Mertens (2012), where shortest-path distances serve
as heuristic features for comparing game states \cite{mertens2012quoridor}. In
the context of this project, these computations may later be reused to support
automated players or provide game analysis features.

\subsection{Algorithmic Complexity}

Although the overall state space of Quoridor is extremely large, the
algorithms used for rule enforcement operate on a fixed-size graph. The number
of vertices is bounded by the number of board squares, and the number of edges
is limited by local adjacency relations.

As a result, graph traversal algorithms such as BFS run in linear time
relative to the size of the board and remain efficient even when executed
repeatedly during gameplay. This makes the proposed approach suitable for
interactive use and ensures that legality checks do not introduce noticeable
delays.

\subsection{Summary}

The combination of grid-based data structures and graph algorithms provides a
robust and conceptually clear foundation for implementing Quoridor. Modeling
the board as a graph allows pawn movement, wall placement, and path validation
to be handled in a unified manner using well-established algorithmic
techniques. This approach is consistent with existing academic work and aligns
with the goals of correctness, efficiency, and extensibility.

\section{Architecture logicielle : MVC}

\subsection{Objectifs architecturaux}
L’architecture du projet a pour objectif de concevoir un moteur de jeu robuste, modulaire et extensible, tout en respectant strictement les règles du jeu Quoridor. Elle doit permettre une bonne testabilité du cœur applicatif, faciliter l’ajout de nouvelles interfaces utilisateur et préparer l’intégration de fonctionnalités avancées telles que l’intelligence artificielle ou le jeu en réseau.

Pour répondre à ces objectifs, nous avons adopté une architecture basée sur le modèle MVC (Model--View--Controller), adaptée au contexte spécifique d’un moteur de jeu.

\subsection{Couche Domaine -- Model}
La couche Domaine correspond au \textbf{Model} du MVC. Elle regroupe l’ensemble des règles du jeu et des structures de données, sans dépendance vis-à-vis des interfaces utilisateur ou des mécanismes d’entrée/sortie.

Elle contient notamment :
\begin{itemize}
    \item \texttt{GameState}, représentant l’état complet d’une partie (plateau, joueurs, murs, tour courant) ;
    \item \texttt{Board} et \texttt{Graph}, assurant la modélisation du plateau sous forme de graphe ;
    \item les entités du jeu (\texttt{Player}, \texttt{Wall}, \texttt{Position}) ;
    \item des modules de validation (\texttt{MoveValidator}, \texttt{WallValidator}) ;
    \item un module de recherche de chemin (\texttt{PathfindingBFS}) permettant de vérifier l’accessibilité du plateau après la pose de murs.
\end{itemize}

Cette séparation garantit que toutes les règles du jeu sont centralisées dans une couche indépendante, facilitant ainsi la validation des règles et les tests unitaires.

\subsection{Couche Application -- Controller}
La couche Application assure l’orchestration globale du jeu et joue le rôle de point de coordination entre les interfaces utilisateur et la logique métier. Elle est principalement incarnée par la classe \texttt{GameService}.

Les responsabilités de \texttt{GameService} sont les suivantes :
\begin{itemize}
    \item recevoir les actions produites par les interfaces utilisateur ;
    \item orchestrer la validation des coups via les modules du domaine ;
    \item appliquer les actions valides à l’état du jeu ;
    \item gérer l’enchaînement des tours ;
    \item détecter les conditions de fin de partie et déterminer le gagnant.
\end{itemize}

Ce choix garantit que toute modification de l’état du jeu passe par un point de contrôle unique, assurant la cohérence globale du moteur.

\subsection{Couche Vue -– Interfaces utilisateur (View)}
La couche Vue regroupe les différentes interfaces utilisateur du projet :
\begin{itemize}
    \item une interface en ligne de commande (CLI) ;
    \item une interface graphique (GUI).
\end{itemize}

Ces interfaces ont pour rôle exclusif de collecter les entrées utilisateur, de les traduire en actions métier et d’afficher l’état courant du jeu. Elles ne contiennent aucune logique métier et n’accèdent jamais directement à la couche Domaine.

Cette organisation rend les interfaces interchangeables sans impact sur le cœur du moteur de jeu.

\subsection{Synthèse}
En conclusion, l’architecture MVC adoptée dans ce projet constitue une base solide pour le développement incrémental du moteur de jeu. Elle permet de garantir une séparation claire des responsabilités, une bonne testabilité du cœur applicatif et une évolutivité compatible avec les extensions prévues par le cahier des charges.
